# 床铺增益建筑通用兼容

> **📦 下载**：[最新版本（Release）](https://github.com/1579486875/UniversalBedFacilityCompat/releases/latest) —— 下载 zip，解压后把整个文件夹放进 RimWorld 的 `Mods\` 目录即可（需要 Harmony）。

> **一句话**：打通模组之间「床」与「床铺家具」的壁垒 ——
> 让你的**模组床**能用上别的模组的衣柜，也让别的模组的衣柜能作用于你的模组床。

- 适用版本：RimWorld **1.6** ｜ 模组版本：**1.0.2**
- 依赖：**Harmony**（`brrainz.harmony`），工坊 2009463077
- 不需要新开存档；旧存档载入后立刻生效
- 移除模组后存档**不残留任何数据**

---

## 你遇到过这种情况吗？

### 方向一：模组添加的床，用不了其他模组的家具

- 你装的这张**模组床**，只认得它自己模组的衣柜；别的模组衣柜摆在旁边**毫无反应**——没有连线，床的属性也没变。
- 换成原版床试试，同一个衣柜又**好用了**。

### 方向二：模组添加的家具，对别的床无效

- 装了个漂亮的**模组衣柜**，说明写着「舒适度 +0.10」，摆在模组床边却装死。
- 而它对自己模组的床、或者原版床，工作得好好的。

**这不是你摆错了，也不是家具坏了。**

RimWorld 要求「床」和「家具」**互相登记备案**：一件家具能作用于哪些床，必须由床那一侧提前把它写进名录。
而模组作者通常只登记了自己认识的那几个（多半是原版的 `Bed` / `DoubleBed`），
一跨界，连接就断了 —— **而且游戏不会报任何错**。

## 它怎么做到的

装上就完事，**不需要任何设置**：

| 它做的事 | 说明 |
|---|---|
| 🔍 **自动认出** | 哪些家具属于「床铺家具」——衣柜、床头柜、屏风、速眠装置、泰迪熊…… |
| 🔗 **双向打通** | **床侧**：每一张床都认得所有床铺家具<br>**家具侧**：每一件床铺家具都作用于所有床 |
| 🛡️ **自动避开** | 工作台工具柜、研究设备等「长得像但不是」的家具，绝不误伤 |
| 🔧 **顺手修正** | 有些家具的链接距离被作者写错（小于一格 = 永远连不上），会自动修好 |
| 🌍 **不看来源** | 原版、DLC、任何模组的床与家具，都在覆盖范围内 |

## 你会得到什么

- ✅ **模组床不再被孤立**：你的模组床能直接吃上其他模组的衣柜、床头柜、屏风
- ✅ **旧存档直接可用**：已经建好的家具会自动接上，**不用拆掉重建**
- ✅ **新装的模组即时生效**：不用等作者更新，不用满世界找兼容补丁
- ✅ **随时可以卸载**：不改动任何模组文件，存档不会残留垃圾
- ✅ **对性能无感**：所有工作都在启动时一次做完，游戏中零开销

## 一、安装与验证

把 `床铺增益建筑通用兼容` 整个文件夹放进：

```
…\RimWorld\Mods\
```

在模组列表里启用（**建议排在所有家具类模组之后**）。压缩包里已经附带编译好的
`Assemblies\UniversalBedFacilityCompat.dll`，直接可用。

### 装好后 30 秒自检

1. **看日志**：启动后日志里应该出现这样一行 ——
   `[UBFC] 扫描完成：床 N 张、床用设施 M 个、新增链接 X 条、重建链接表 Y 份。`
   出现了就说明引擎跑起来了。
2. **看连线**：进入存档，**点选**一个衣柜/床头柜。如果它确实作用于旁边那张床，
   游戏会从它画一条线连到床上；没有线就说明没链接上。
3. **看报告**：选项 → 模组设置 → 床铺增益建筑通用兼容。
   勾上「输出详细诊断日志」再点「立即重新扫描」，
   下方报告会列出识别到的**设施清单**与**床清单**（defName）。
4. **看床的信息面板**：选中床，在「设施」一栏里应当能看到作用于它的家具名字。

第 3 步是排查问题最有效的手段：**先看目标家具在不在设施清单里，再看目标床在不在床清单里**，
一眼就能定位是「没被识别」还是「识别了但放置条件不满足」。

## 二、设置项

游戏内「选项 → 模组设置 → 床铺增益建筑通用兼容」：

| 设置 | 默认 | 说明 |
|---|---|---|
| 进入地图时自动重新链接 | 开 | 让旧存档里早就建好的家具立刻生效，不必拆除重建 |
| 输出详细诊断日志 | 关 | 在日志里打印扫描统计与明细，排查「为什么不生效」时打开 |
| 激进模式 | 关 | 所有带 `CompProperties_Facility` 的家具都参与床铺链接 |
| 忽略链接数量上限 | 关 | 放开「每张床同种设施只能生效一个」的原版限制 |
| **修正过小的链接距离** | **开** | 把 `maxDistance` 小于一格（如 0.9）的床用设施抬到 2 格，见第三节 |
| 立即重新扫描 | — | 让上面几项**立刻生效**，不必重启游戏 |

后四项会改变 Def 数据本身，改完点一下 **立即重新扫描**：

- 引擎会先从基线完整还原，再按当前设置重新注入 —— 所以反复切换、反复点也不会累积污染；
- 如果此刻正在游戏中，扫描完成后会**顺带刷新地图上已经建好的家具**，
  改动立刻可见，不需要退出重进地图。

> ⚠️ 开启「激进模式」意味着工作台用的工具柜之类也会去链接床。
> 它不会破坏存档，但会让一些原本只服务工作台的家具出现在床的连线里，
> 请只在你确实需要时开启。

## 三、常见疑问

### 服务医疗床的「健康增益建筑」会被纳入吗？会和普通床混用吗？

**会纳入，且不会混用** —— 区分是原版自己做的，本模组既不需要也无法干预。

- 判据里本就包含 `canLinkToMedBedsOnly`（绑医疗床标志），这类设施会被识别为床用设施；
  即使作者没写这个标志，只要它原本就挂在医疗床上，也会通过「基线链接表里含床」被识别。
- 本模组把设施注入到**所有**床的白名单（Def 层面），但**真正建立链接时原版会再检查一次**：
  `CompAffectedByFacilities` 遇到带 `canLinkToMedBedsOnly` 的设施时，要求对方必须是
  `Building_Bed { Medical: not false }`，否则直接拒绝。所以普通床拿不到医疗设施的效果。
- 切换是**动态**的：`Building_Bed.Medical` 的 setter 会调用 `FacilityChanged()`，
  它双向触发 `Notify_ThingChanged()` 重链。所以你随时把一张普通床切成医疗床，
  旁边的医疗设施会立刻连上去；切回去也会立刻断开。

### 囚犯床 / 奴隶床 / 访客床能享受增益建筑吗？

**能，且不需要任何额外处理。**

床的归属（殖民者 / 囚犯 / 奴隶 / 访客）是 `Building_Bed` 的**运行时属性**
（`ForOwnerType`、`Medical`），不是 Def 属性。同一张 `Bed` 无论分配给谁，
共享的都是同一个 Def 级别的 `linkableFacilities` 白名单。

而且 `CompAffectedByFacilities` 的源码里**完全没有** Prisoner / Slave / Guest /
ForOwnerType / Assignable 相关判断 —— 链接机制根本不看归属。

> 唯一前提：这些床所在的 Def 必须带 `CompProperties_AffectedByFacilities`。
> 本模组不替缺组件的床添加组件（那属于床模组的责任），
> 但会在日志与设置界面里明确列出这类床。

### 床放在飞船上，飞船换地图之后还能连上吗？

**能。**

- **起飞**：`GravshipUtility` 会对飞船上每个 Thing 先调 `PreSwapMap()`，
  再 `DeSpawn(DestroyMode.WillReplace)`；`CompFacility.PostDeSpawn` → `UnlinkAll()` 干净解绑。
- **降落**：`GravshipPlacementUtility.PlaceGravshipInMap` → `SpawnNonPawnThings`
  用的是标准 **`GenSpawn.Spawn(...)`**，于是 `PostSpawnSetup` 被正常触发，
  设施侧 `LinkToNearbyBuildings()` 与床侧 `LinkToNearbyFacilities()` **双向重建**，
  与 Spawn 顺序无关；而且 `LinkToNearbyBuildings()` 一开头就会 `UnlinkAll()`，不会残留旧链接。

顺带一提：飞船自己的设施组件 `CompGravshipFacility` 是 `CompFacility` 的子类，
但它服务的是重力引擎、基线链接表里没有床，因此不会被误判成床用设施。

### 有些家具明明贴着床，却始终连不上？

先看它的 `maxDistance`。**格子的最小间距是 1**，如果作者把这个值写成了小于 1 的数
（例如 GloomyFurniture／复古家具的泰迪熊 `GL_Teddy` 是 `0.9`），那么在机制上它就等价于
「必须和床占同一格」——放在相邻格时水平分量已经有 1.0，距离判定必然超标，于是**永远连不上**。

这类值几乎不可能是刻意设计（作者的意图通常就写在自家床的白名单里，例如
`GL_Teddy` 确实出现在 GloomyFurniture 各张床的 `linkableFacilities` 中）。

因此「修正过小的链接距离」这个设置**默认开启**，会把取值落在 `(0, 1)` 开区间内的
床用设施抬到 **2 格**，让紧邻的床也能生效。只碰这个区间：

- `maxDistance = 0` 表示「不接受任何链接」，不动
- `maxDistance >= 1` 都是作者的有效意图，不动
- 带「必须相邻」约束的设施根本不走距离判定，跳过以免制造无用改动
- 若 `minDistance` 本身不小于目标值，抬高 `maxDistance` 只会得到空区间，同样跳过
- 关掉开关后，会从基线**精确还原**成原值

### 和工坊上的 `Linkable Groups` 是什么关系？

`Linkable Groups`（工坊 3659197870）解决的是**同一个痛点**，但走的是另一条路：
它靠**手工维护的分组列表**（"Cooking" / "Smithy" 等）替玩家把连接写好，
覆盖面更广（不只是床，还有工作台、熔炉等），代价是**每出一个新模组就要作者跟进**。

本模组走的是**自动推断**：从家具原本的链接表反推它是不是床用设施，
**零维护、新模组即时生效**，但范围专注在**床铺设施**上，且需要防误判。

两者可以**同时安装**——都是"只添加、不删除"的写法，各管一侧还能互补。

## 四、原理：RimWorld 的设施链接是怎么回事

> 以下内容面向想深入了解机制的玩家与模组作者。

RimWorld 1.6 里，一件家具能作用于哪些床，**不是由家具自己决定的**。

`CompProperties_Facility.linkableBuildings` 是一个 `[Unsaved]` 字段，它**不读 XML**，
而是在 Def 加载时由 `ResolveReferences()` 反向推导：

```
linkableBuildings = { 所有 Def D | D.linkableFacilities 中包含我自己 }
```

也就是说 ——「衣柜能作用于哪些床」完全由「**床那一侧的白名单**」单方面决定。
家具模组通常只往原版 `Bed` / `DoubleBed` 上打补丁，于是同一种衣柜对模组床就失效了。

**这个单向设计会让问题从两个方向冒出来**：

| 方向 | 你看到的现象 | 根本原因 |
|---|---|---|
| **模组的床 → 外面的家具** | 这张床不认识别的模组的衣柜 | 床的名录里只写了自己模组的设施 |
| **模组的家具 → 外面的床** | 这个衣柜对模组床装死 | 作者只把衣柜登记到了原版那几张床上 |

两个方向**根因相同**：连接能不能建立，取决于「床」有没有把「家具」写进自己的名录，
而这件事基本靠模组作者互相认识 —— 跨界就断。

**本模组的对策**是在全部 Def 加载完成后，**替两边都把名录补全**，
让「谁登记了谁」不再取决于作者认不认识对方。

## 五、它具体做了什么（六个阶段 + 重链 + 完整性自检）

| 阶段 | 做什么 |
|---|---|
| 1. 分类 | 找出所有床（`def.IsBed`）与所有设施（带 `CompProperties_Facility`），留下基线快照 |
| 2. 判定 | 识别「床用设施」，并迭代吸收使用自定义 `thingClass` 的「伪床」 |
| 3. 注入 | 把床用设施写进每一张床的 `linkableFacilities`；登记并集、还原已退场的建筑 |
| 4. 重建 | 按原版语义重算设施的 `linkableBuildings`（并集策略，只增不减） |
| 5. 上限 | 可选地覆盖 `maxSimultaneous` 链接上限 |
| 6. 距离 | 可选地把「小于一个格子」的 `maxDistance` 抬到能覆盖相邻格的范围 |

### 怎么识别「床用设施」

这一步是关键，做错就会把工作台的工具柜接到床上。采用三重信号投票，命中任一即认定：

| 信号 | 说明 | 举例 |
|---|---|---|
| **A**（主判据） | 它的原始链接表里含至少一张床 | 作者确实把它接到了床上，最可靠 |
| **B** | 带明确绑床的放置约束标志 | 原版 `EndTable` 用的就是 `mustBePlacedAdjacentCardinalToBedHead` |
| **C**（可选） | 激进模式，一律认定 | 用来收拾「作者忘了挂接任何床」的家具 |

反例：原版 `ToolCabinet` 三条都不满足（它服务的是工作台），因此**不会被误伤**。

**伪床的资格审核**：少数模组的「床」用自定义 `thingClass` 实现，导致 `def.IsBed == false`。
本模组要求这类候选者**确实具备床的特征**（挂着 `CompAssignableToPawn_Bed`，
或建筑数据里开启了床专属字段）才会把它当成床 —— 这道把关是为了防住
「研究台被误当成床、进而把它服务的家具也连带判成床用设施」的连锁误判
（原版 `Building_ResearchBench` 直接继承 `Building`，并不由 `Building_WorkTable` 覆盖）。
真正的 `Building_Bed` 子类不受这道审核影响。

### 关于「重链」

上面六步改的是 **Def 数据**，但链接关系是建筑 `SpawnSetup` 时**现场建立**的，
所以还需要一步把改动落到**地图上已经建好**的家具身上：

- 旧存档载入后，由 `CompatGameComponent` 在首个 tick 触发一次；
- 玩家在设置界面手动「立即重新扫描」时立刻触发一次。

它遍历的是「改过的对象」并集，因此连**退场**的设施（例如关掉激进模式后的工具柜）
也能被解开残留链接。

### 关于「完整性自检」

本模组的扫描挂在 `StaticConstructorOnStartup` 上，而 RimWorld 是按**模组加载顺序**
逐个调用静态构造的。也就是说，只要有一个排在后面的模组也去重建同一批白名单
（他们要把自家新家具接上自家新床时就会这么做），本模组写下的注入就会被无声抹掉。
Harmony 保险丝只覆盖「`ResolveReferences` 又被调用」这一条路径，覆盖不了直接赋值。

所以游戏开始后的第一个 tick 还会做一次**只读检查**：确认每张床的白名单里仍然写着
全部床用设施、每件床用设施的白名单里仍然写着全部床。一旦发现被改写，就地重做一遍
注入与重建 —— 这两步都是幂等、从基线重建的，重做不会累积污染。

已实测：当前这 1091 个启用模组里，所有会在代码里碰这套白名单的模组（3204 个程序集
里的 70 个，逐个用 IL 元数据核对过）**加载顺序都排在本模组之前**，所以这次自检
不会触发。它防的是别的模组组合。

### 关于「基线」

四张基线表都只在第一次扫描时采集，之后永不更新。它们有两个作用：

- 判定时用它，避免把本模组自己的注入误当成「作者本来就连了床」的证据；
- 重新扫描时从它精确重建，保证反复切换设置不会累积污染。

## 六、性能

这个模组刻意**没有**把补丁挂在任何热路径上。

| 环节 | 时机 | 成本 |
|---|---|---|
| 扫描 + 注入 + 重建 | 启动时一次 | O(Def 数)，实测量级为几十毫秒 |
| 重新链接旧家具 | 每次进入地图后的**第一个 tick**，一次 | 按 Def 索引取实例，不遍历整张地图 |
| 完整性自检 | 游戏开始后的**第一个 tick**，一次 | O(床数 × 设施数) 次哈希查询，通过后永久短路 |
| Harmony 补丁 | 只在 `ResolveReferences` 这条 **Def 加载冷路径** | 一次哈希查找 |
| 每 tick 的持续开销 | `GameComponentTick` 里一次 `bool` 判断，首 tick 后立即短路 | 可忽略 |

几个刻意的取舍：

- **不做全地图遍历。** 链接查找依旧走原版的 `listerThings.ThingsOfDef`（字典索引），
  候选集合大小只和「地图上实际存在的家具数量」有关，和注入的 Def 数量无关。
- **只重链设施一侧。** 因为 `CompFacility.LinkToNearbyBuildings()` 会为每个候选床
  双向建立链接，且不像被影响方那样用 LINQ 排序，成本更低 —— 这也正是原版
  `PostMapInit` 的做法。
- **重建链接表用单遍扫描。** 把原版 O(设施数 × 全 Def 数) 的推导降到
  O(全 Def 数 × 白名单长度)，结果集合与顺序和原版完全一致。
- **Harmony 补丁不参与核心功能。** 即使 Harmony 装载失败，兼容效果一样完整，
  只是少了一层保险。

## 七、为什么需要那一个 Harmony 补丁

`linkableBuildings` 是按「床侧白名单」推导的。如果游戏运行期间有任何人
重新调用 `ResolveReferences` —— 例如 `PlayDataLoader.HotReloadDefs()`（热重载）、
其他模组的动态 Def 处理、开发者工具 —— 推导结果就会退回成「只覆盖原版床」，
本模组的效果会被**悄悄抹掉**。

补丁挂在 `CompProperties_Facility.ResolveReferences` 的 Postfix 上，
会把**两侧**都补齐回去：

- 设施侧 `linkableBuildings` —— 保证设施仍能主动发现全部床；
- 床侧 `linkableFacilities` —— 保证床侧发现与放置预览连线不失真。

它是纯粹的保险丝 —— 核心功能完全不依赖它。

## 八、兼容性与已知限制

**兼容**

- 原版及其全部 DLC（Royalty / Ideology / Biotech / Anomaly / Odyssey）
- 使用自定义 `CompProperties_Facility` 子类的模组（重建时采用并集策略，只增不减，
  不会破坏子类自己写入的内容）
- 界面与日志提供 **简体中文 / 繁體中文 / English**，跟随游戏的当前语言自动切换；
  其他语言会回退到 English
- 不修改任何 Def 的 XML 文件

**关于存档**

链接关系**不入档**，每次载入现场重建，所以本模组的效果不依赖存档内容。
唯一会写进存档的是本模组的 `GameComponent` 登记项（RimWorld 对
`Game.components` 使用 `LookMode.Deep` 序列化）。

这意味着：**卸载本模组后用旧存档进入**，日志里会出现一条
「找不到 `UniversalBedFacilityCompat.CompatGameComponent`」的提示。
RimWorld 随后会自动把它清理掉，游戏照常进行，可以安全忽略——这是所有带程序集的
模组共有的现象，不代表存档被污染。

**加载顺序**

本模组在全部 Def 加载完成后统一扫描，绝大多数情况下与排序无关。

唯一的例外是「排在后面的模组在自己的 `StaticConstructorOnStartup` 里重建了同一批白名单」，
这种改写会发生在扫描之后。你不必为此操心 —— 游戏开始后的第一个 tick 会检查一次，
发现被改写就地补回来（见第五节「关于完整性自检」）。仍然建议把本模组排在
所有家具类模组之后：这样连那次补救都不必发生。

**两个真实案例**

- **GloomyFurniture 的泰迪熊**（`GL_Teddy`）：作者确实想让它给床加舒适度，也把它写进了自家床的
  白名单，但 `maxDistance` 写成了 `0.9`。格子的最小间距是 1，所以它**永远连不上任何床** ——
  连作者自家的床也连不上。第六阶段的距离修正就是为它做的。
- **[MUS]太空基地家具 的床**：它的床只登记了自家那几件家具和原版的速眠装置，
  原版的衣柜、床头柜摆在床边毫无反应，而且游戏不会报任何错。
  本模组会把这份名录补全 —— 那些床照样能用上原版与所有模组的家具。

**已核验的边界情况**

下面这些场景都对着 RimWorld 1.6 的反编译源码逐条走过一遍，不是推测：

| 场景 | 结论 |
|---|---|
| 床侧白名单为 `null`（XML 里就不写这个字段） | 会被换成新列表之后才注入，因此照样生效 |
| `maxDistance` 为 0 / ≥1 / 负数 / NaN | 一律不动 —— 只处理 `(0, 1)` 开区间 |
| `minDistance` 已经大于修正目标 | 不动，否则会得到一个空的合法区间 |
| 带相邻约束的设施（`mustBePlacedAdjacent*`） | 不改它的 `maxDistance`：原版那段距离判定对它们根本不执行 |
| 多个 Def 共用同一个 `CompProperties` 实例 | 重建时按实例聚合，不会被覆盖 |
| 自定义 `CompProperties_Facility` 子类 | `GetCompProperties<T>` 用 `is T` 判定，子类一并命中 |
| 囚犯床 / 奴隶床 / 访客床 | 天然支持 —— `CompAffectedByFacilities` 里没有任何一处引用床的归属类型 |
| 医疗床在运行时切成普通床（或反过来） | 由原版 `Building_Bed.FacilityChanged()` 双向重链，本模组不介入 |
| 家具拆下再装回、飞船换地图 | 都走 `SpawnSetup` / `PostMapInit`，链接现场重建 |
| 开发者模式的 Def 热重载 | 安全：`LoadedModManager` 热重载时复用原 Def 实例，只是把新数据浅拷贝进去，保险丝仍认得出它 |
| 排在后面的模组重建了白名单 | 首个 tick 的完整性自检会补回来 |

**限制**

- 如果某张床**完全没有** `CompProperties_AffectedByFacilities` 组件，设施在机制上
  无法附着于它。这必须由那张床所属的模组补上，本模组无法代为处理 ——
  但会在日志与设置界面里明确告诉你有哪些床属于这种情况。
- 如果某件家具**只**连接了特征不明确的自定义建筑、自身又不带任何绑床约束，
  默认模式下无法确认它的用途 —— 这是刻意的保守设计。
  遇到这种情况请开启「激进模式」：它会把判据放宽到全部设施，
  同时仍然保证工作台类建筑与不具备床特征的建筑绝不会被当成床。
- 「忽略链接数量上限」开启后，家具信息面板仍会显示原始的「每个建筑最大链接数」，
  这是显示层面的问题，不影响实际效果。
- 如果一个 Def **既是床、又是床铺家具**（同一件建筑同时挂 `CompAffectedByFacilities`
  和 `CompProperties_Facility`），它会把自己写进自己的白名单，表现为给自己加属性。
  原版的链接判定本来就不禁止自链接，本模组只是让「白名单包含全部床用设施」成为必然，
  于是这种情况会实实在在地发生。本模组**不做特殊处理**——否则「同种家具之间互相加成」
  会被一起掐掉。只在开启详细日志时提示有几个这类 Def。
  实测当前 1091 个启用模组中并未出现这种 Def。

## 九、排查「某个柜子对这张床还是不生效」

1. 打开设置里的「输出详细诊断日志」，点「立即重新扫描」，查看报告里的设施清单与床清单。
2. 检查这件家具是否在**设施清单**里。不在 → 它没被判定为床用设施，
   试试开启「激进模式」再重新扫描。
3. 检查这张床是否在**床清单**里。不在 → 它十有八九缺少
   `CompProperties_AffectedByFacilities`，报告里会有专门的提示。
4. 两个清单都有却仍不生效 → 通常是**放置约束**问题（比如床头柜必须紧贴床头、
   屏风要求视线通畅），或者 `maxDistance` 被写得太小（见第三节）。
   前者属于家具作者的设计意图，本模组刻意不干预。

## 十、人工排除（逃生舱）

如果自动判定出现误判，可以点名排除。在自己的模组里打个补丁即可：

```xml
<Operation Class="PatchOperationAdd">
  <xpath>Defs/UniversalBedFacilityCompat.CompatPolicyDef[defName="UBFC_DefaultPolicy"]/excludedFacilities</xpath>
  <value><li>SomeMod_DecorativeDresser</li></value>
</Operation>
```

- `excludedFacilities` —— 这些家具不参与通用床铺链接
- `excludedBeds` —— 这些床保持原版行为

## 十一、自己编译

需要 .NET SDK 与 RimWorld 本体的程序集。在 `Source\` 目录下：

```powershell
dotnet build UniversalBedFacilityCompat.csproj -c Release `
  -p:RimWorldDir="<你的 RimWorld 安装目录>" `
  -p:HarmonyDll="<0Harmony.dll 的完整路径>"
```

产物会自动输出到 `..\Assemblies\UniversalBedFacilityCompat.dll`。

`0Harmony.dll` 通常在以下位置之一（`csproj` 会自动探测前三个）：

- `<RimWorld>\Mods\Harmony\Assemblies\0Harmony.dll`
- `<RimWorld>\Mods\0Harmony\Assemblies\0Harmony.dll`
- `<RimWorld>\RimWorldWin64_Data\Managed\0Harmony.dll`
- 创意工坊：`…\workshop\content\294100\2009463077\Current\Assemblies\0Harmony.dll`

目标框架必须是 **net48**。所有游戏程序集都标了 `<Private>false</Private>`，
不会被复制到输出目录。

### 源码结构

| 文件 | 职责 |
|---|---|
| `CompatBootstrap.cs` | 启动引导，`[StaticConstructorOnStartup]`，只在 Def 全部加载完成后调用引擎 |
| `CompatEngine.cs` | **核心**：分类 → 判定 → 注入 → 重建 → 上限 → 距离，六阶段全在这里；另外提供重链与完整性自检的入口 |
| `CompatGameComponent.cs` | 游戏开始后的第一个 tick 做一次完整性自检；进入地图后重新链接一次，让旧存档立刻生效 |
| `HarmonyPatches.cs` | 唯一一处补丁，`ResolveReferences` 的保险丝 |
| `CompatMod.cs` | 模组入口：装载 Harmony + 设置界面 |
| `CompatSettings.cs` | 设置数据 |
| `CompatPolicyDef.cs` | 排除清单 Def，供误判时人工干预 |
